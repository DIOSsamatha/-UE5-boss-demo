## 第六轮：用户报"移动时没有动画，就是模型平移" —— 速度来源取错 + 倍速误套到 Idle
- 用户反馈"移动时没有动画，只有模型平移"。又是靠日志定位，不是靠猜。
- **真凶 A：`GetVelocity()` 在 ACharacter::Tick 里读到的永远是 0。**
  - 证据：`[Boss][动画] 切换位移动画` 行每一条都是「原始速度=0」，而同一时刻 Brain 自己打的
    `[Boss][移动]` 行是「速度=380」。原因是 `RequestDirectMove` 的速度已被 CharacterMovement 消费掉。
  - 后果链：`SmoothedLocoSpeed` 长期趋近 0 → 播放倍速被死死钉在下限 0.75
    → 腿只按 0.75 倍速慢动作爬（脚速≈277cm/s），胶囊仍 380cm/s 平移 → **"没有动画只是模型平移"**。
  - 修法：速度的【下达者】是 Brain，让它把速度传进来。
    `NotifyBossMoveCommand()` → `NotifyBossMoveCommand(float CommandedSpeed)`（public，Brain 跨类调用），
    新增成员 `LastMoveCommandSpeed`；`UpdateBossLocomotion` 里移动中用 `LastMoveCommandSpeed`、停住才退回 `GetVelocity()`。
- **真凶 B：播放倍速被误套用到 Idle。**
  - 原来不管播什么都 `ComputeLocoPlayRate(SmoothedLocoSpeed)`，停住时速度≈0 → 倍速=下限 0.75
    → **待机动画以 0.75 倍慢动作播放**，看起来同样像"没在动"。
  - 修法：`bDesiredIsJog ? ComputeLocoPlayRate(SmoothedLocoSpeed) : 1.f`。
- **真凶 C：滤波把起步吃掉了。** 即便速度来源修对，`FInterpTo` 从 0 爬到 380 要 ~0.5s，
  每次进 Jog 第一帧仍是 0.75。修法：移动中**直接采纳**指令速度（BOSS 指令速度恒定、本无抖动，无需滤波），
  只有"停"才用 `FInterpTo(...,5.f)` 慢衰减让腿自然收步。
- 新增 `[Boss][姿势诊断]` 日志：把 `ShouldTickPose()` 的每个子条件（已注册/有Anim实例/未暂停/允许骨架更新/世界已初始化/可见性选项）单独打出。

  ⚠ 这也说明"骨骼每次移动=0.0cm"在无头环境下不可信，别拿它当"动画没动"的证据（无头不渲染，姿势可能真没求值）。
- 验证（`python Tools/RunHeadlessGame.py 65` 后 grep 日志）：Idle 稳定 `速率=1.00`；Jog 满速 `速率=1.03`（=380/370，正确）。

## 第七轮（真正的系统性根因，两处）：Actor/Mesh 空间错位 90° + 骨骼变换从不刷新
- 用户第三次说"移动还是没有动画、只是模型平移"。这次不再猜，直接加诊断把"事实"打出来。
- **★ 真凶 1：Mesh 带 Yaw = -90° 相对旋转，而方向判定用的是 Actor 空间。**
  - 诊断日志：`Mesh相对旋转=(Pitch0,Yaw-90,Roll0) | 世界前向在Actor空间=(1.00,0.00) 在Mesh空间=(-0.00,1.00)`
  - 含义：动画的"前"是 Mesh 本地轴。我们用 `GetActorTransform().InverseTransformVectorNoScale(Vel)`
    算出的"前"，实际喂给了动画的【侧】轴 → BOSS 朝玩家直冲却播侧向/倒退的腿。
  - 这就是前几轮调脚速(370)、朝向(bUseControllerDesiredRotation)、换向死区**全都打偏**的根因——那些修复本身没错，但被 90° 错位盖住了。
  - 修法：`PickLocoJogSequence()` 改用 `MeshComp->GetComponentTransform().InverseTransformVectorNoScale(Vel)`；
    骨骼测量的 `InverseTransformPosition` 同样改成 Mesh 空间。
- **★★ 真凶 2：`VisibilityBasedAnimTickOption` 设成了 `AlwaysTickPose`，它【不刷新骨骼变换】。**
  - 枚举语义（`SkinnedMeshComponent.h:93`）名字骗人：
    - `AlwaysTickPoseAndRefreshBones(0)`：不管渲不渲染都 tick 姿势**并刷新骨骼变换**
    - `AlwaysTickPose(1)`：都 tick 姿势，但**只有被渲染时才刷新骨骼**
  - 设成 1 时，一旦未被渲染（背身/远处/遮挡，或无头 -NullRHI），骨骼变换停在参考姿势：
    实测脚骨 `foot_l` 世界 Z 恒为 18、Mesh 空间位移恒 `0.0cm`，而世界位移恰等于身体位移（190cm/0.5s=380cm/s）
    → 就是"腿一动不动跟着身体平移"。单节点没有 AnimBP 兜底，骨骼不刷新 = 画面完全不更新。
  - 修法：改为 `AlwaysTickPoseAndRefreshBones`。
- **诊断方法订正（我自己的测量错误）**：之前用 **手骨** `hand_r` 判断"动画有没有动"，
  走路时手几乎不动 → 一直得出"骨骼 0.0cm = 动画没动"的错误结论，误导成"姿势 tick 问题"。
  改用**脚骨**（`foot_l`/`foot_r` → `calf_l/calf_r` → 兜底）后才是有效证据。
- **修复验证（同一份日志对比，`角色空间位移`）**：
  - 修前：Jog 段恒 `0.0cm`（腿冻住）
  - 修后：Jog 段 `64.7cm / 89.0cm`，Idle 段 `~0.1cm`（待机本来就不动）→ 腿真的在迈步了
- 编译坑（UE 5.7 LWC）：`GetRelativeRotation()` **已经直接返回 `FRotator`**，不要再 `.Rotator()`（C2039/C2737）；
  `GetBoneLocation()` 要传 `FName` 不能传 `int32` 索引（C2664），用 `GetBoneName(idx)` 转。

## 第九轮（真相）：播放时间每 ~3s 归零一次 → 一定是【蒙太奇抢占】而非行走逻辑
- 用户明确纠正："不是瞬移，boss 模型都不动的，移动时是整体模型在地面上平移" → 这条描述很关键。

  ```
  Idle_NonAdditive        54  57.4%
  Jog_Fwd                 8   8.5%   ← 行走动画只占 8.5%！
  Boss_Guard_Idle_Montage 7   7.4%

  ```
  → **BOSS 几乎从不走路**：57% 待机 + 大量攻击蒙太奇，行走只占 8.5%。
  → 玩家看到的"整体在地面平移"其实主要是【攻击蒙太奇自带的根位移】，不是行走动画。
- 另一个决定性线索：`Jog_Fwd 时间` 反复 `0.00 / 0.26 / 0.39 / 0.02 / 0.17 / 0.12` ——
  **播放时间每 ~3s 就归零一次**，说明单节点槽位被别的东西反复抢占。
  在 `IsAnyMontagePlaying()` 为真时 `UpdateBossLocomotion` 直接 return（"不打扰"），
  蒙太奇结束后才切回行走 → 每次切回都是从第 0 帧重播，腿永远走不完一个完整步态。
- ⚠ 所以"滑步"的观感 = 攻击蒙太奇根位移 + 行走动画被频繁打断重播，两者叠加。
- 排查工具沉淀：一个正则统计资产分布就能一眼定性
  `re.findall(r'anim自检\] 单节点资产=(\S+?) 时间', log)` + `Counter`。
  **别只看某一帧就下结论，要统计整局的"哪个动画占多少时间"。**

## 第十八轮：锁定视角时，出招期间增加【弱跟随】朝向修正（治"连打打到空气"）
- 需求：锁定视角时攻击也要弱跟随 BOSS，不至于连续攻击越打越歪打到空气去。
- **根因**（`LockOnComponent.cpp` 第 420 行附近）：出招期间（`State_Attacking`）直接
  `return;` —— **完全不管身体朝向**。当时这么写是为了修"出招时镜头疯狂乱摇"，
  但代价是：连打时朝向完全失控（招式自己控面），玩家绕圈连打身体越歪越远 →
  后续攻击全砍空气。两个需求（不乱摇 / 不打空）被做成了互斥。
- **修法（折中，不是二选一）**：出招期间改做**弱跟随**，三个条件同时成立才纠偏：
  1. 转向速度 = `TurnSpeed / AttackTurnSpeedScale`（常态 11 → 出招期间 2.75 度/秒，非常"懒"）
     → 不足以和招式根运动抢方向盘，镜头不会乱摇。
  2. 偏差 < `AttackTurnAngleThreshold`（30°）时**完全不动**
     → 绝大多数帧都不碰身体，镜头彻底安静（这是防抖关键）。
  3. 只有偏差大到"攻击明显打空"才用 `RInterpTo` 慢慢拉回。
- 新增两个可调参数（`LockOnComponent.h`，`Demo|LockOn` 分类）：
  `AttackTurnSpeedScale = 4.f`、`AttackTurnAngleThreshold = 30.f`。
- 非锁定态（`bDriveOwnerRotation` 关 / 目标丢失）行为不变；出招期间也仍受常态死区保护。
- 构建 exit 0。
- ⚠ 调参指引：还打空 → 把 `AttackTurnAngleThreshold` 调小（20~25）或 `AttackTurnSpeedScale` 调小（3）；
  镜头又开始甩 → 反向调大。

## 第十九轮：预警红光阶段跟随玩家移动（带行走动画）+ 修一个分类误读
- 需求："boss出招时不移动，在预警红光时跟随玩家，也要有移动动作动画"。
- **改动 1：只有【真正出招】才定身**
  新增 `ABossCharacterBase::IsStrikeActive()` —— 以 **Brain 状态机** 为准
  （`GetState() == EBossState::Attack`），**不含 Telegraph / Recover**。
  `DriveMoveNoNav` 里的定身判据从 `IsAttacking()` 改成 `IsStrikeActive()`。
  ⚠ 不能只看 GAS 标签 `State_Attacking`——它覆盖"预警→出招→后摇"整段。
- **改动 2：删掉进预警时的 `StopMovement()`**
  `OnStateChanged` 的 `case EBossState::Telegraph` 原来第一句就站死（注释写"动来动去玩家读不出招"）。
  现在预警期间**继续跟随玩家移动 + 播行走动画**（压迫感 + 玩家能预判落点），
  真正挥出那一瞬间才定身。
- **改动 3（★隐蔽 bug，第十七轮引入的）**：`UpdateBossLocomotion` 里的
  `if (AnimInstance->IsAnyMontagePlaying()) return;`
  —— **行走本身现在也是蒙太奇**！所以这个条件在【走路时同样为真】，
  导致每帧都走进"让招式播完"的早退分支，**永远走不到下面的行走播放逻辑**
  → 表现为"只有追击中动一下，出招期间完全没动画"。
  修法：判据改成"除【自己的 5 个行走蒙太奇】外还有没有别的蒙太奇在播"
  （`bOtherMontagePlaying = IsAnyMontagePlaying() && !bIsOwnWalkMontage`）。
  ⚠⚠ 教训：**把某个系统从"序列"改成"蒙太奇"时，必须复查所有 `IsAnyMontagePlaying()` 判据**——
  它原来的语义是"有没有表演动画在播"，现在会把自己的动画也算进去。
- **验证**：
  - 预警期间确实在动：`Boss_Guard_Idle_Montage 速度=380`、`Boss_Slash_01_Montage 速度=380`。
  - 行走蒙太奇**确实与攻击蒙太奇同时在播**（这正是 DefaultSlot 分层混合该有的表现）：
    `Boss_Slash_01_Montage + Boss_Walk_Fwd_Montage : 4`
    `Boss_Slash_02_Montage + Boss_Walk_Fwd_Montage : 4`
    `Boss_Spin_01_Montage  + Boss_Walk_Fwd_Montage : 4`
- ⚠⚠ 统计口径陷阱（差点误判成"修复失败"）：
  脚本按"单节点资产是不是 Jog"来判"腿上有没有动画"，而现在**行走也是蒙太奇**，
  单节点资产那一栏显示的是**攻击蒙太奇** → 于是统计出"移动中腿上没动画 = 100%"，
  看起来像没修好。**正确判据要看 `蒙太奇=` 那一栏是否含 `Boss_Walk_*`**。
  以后写统计脚本要先确认"哪个字段代表行走动画"，别想当然。

## 第二十轮：命中窗口空档 + 四向行走方向源失效 + 闪避距离
- **改动 1：命中窗口可能开 0 帧（用户"攻击了却没伤害、也弹不了"）**
  `SetupMeleeHitWindow` 原来：`WaitDelay(this, FMath::Max(EndTime, StartTime + 0.05f))`。
  开窗任务在 `StartTime` 触发、关窗任务在 `max(EndTime, StartTime+0.05)` 触发，
  **两个任务靠同一时间轴竞争**；一旦某招 `EndTime <= StartTime`（比例没配好/被夹到同一点），
  关窗紧跟开窗同帧触发 → 窗口开 0 帧 → "挥了但没伤害、不能弹反"。
  修法：① 先夹非空区间；② 强制 `MinWindow = 0.12s`；③ 窗口放不下就把开窗点整体前移。
  并**加一行日志** `[Boss] 命中窗口「招式」: 开=x 关=y 时长=z`。
  验证：7 条窗口，**最短 0.250s / 最长 1.030s**（Spin_01 转身 1.03s、Throw_01 0.80s）。
- **改动 2：四向行走只播 Fwd（用户"要有各个方向的动画"）**
  方向判定的数据源 `MoveDeltaThisFrame` **只在"非蒙太奇分支"里更新**；
  而蒙太奇分支占了绝大多数帧 → 它一直保留老值甚至恒为 0 → 方向判定失效 → 只播前冲。
  修法：蒙太奇分支里也更新 `MoveDeltaThisFrame`。
  另外删掉 `PickLocoWalkMontage` 里的 `if (!Cur) return Fwd;` ——
  "当前没播蒙太奇"恰恰是【静止→起步】、最需要判方向的时刻。
  方向源改为三级回退：① 实测位移 ② `LastMoveCommandDir` ③ `PlayingLocoLocalDir`（上次方向）。
- **改动 3：闪避距离 120 → 150**
  ⚠⚠ 同时把 `DodgeDistanceMax` 150 → **200**。原来 `DodgeDistance(150) == Max(150)`，
  谁把距离调大都会被"夹"回 150（日志实证："DodgeDistance=120 被上限夹到 150"），导致改不动。
  ⚠ **改这类值必须同时改蓝图 CDO** —— 蓝图子类序列化值优先于 C++ 默认值，
  只改 C++ 画面完全不变（已在头文件写明）。
- ⚠ 遗留事实（**诚实记录，不是 bug**）：无头跑实测行走蒙太奇**仍然只有 Fwd**。
  原因不是代码，而是 BOSS 的行为特性：
  它由 Brain 持续 `SetActorRotation` 转向玩家 + 绕圈半径很近（实测 87% 时间在 200~400cm），
  所以移动方向相对**自身朝向**几乎总是"前"→ Mesh 空间里 `Local.X >= 0` 恒成立 →
  判据 `AbsF >= AbsR` 永远走前冲分支。四向素材齐全，只是这些条件下用不到。
  → 想看到侧向动画需要 BOSS 真正横移（大半径绕圈 / 玩家站到侧面），
    或调大 `StrafeDistance`。**空步的观感也因此改善**（不再"侧着走却播前冲"）。

## 第二十一轮（★"攻击没伤害"的真正根因，靠日志取证一次性解决）
- 用户连说"还是不行"并要求一次性解决。停止调参数，改为**先取证**。
- **★决定性证据（无头日志）**：
  ```
  [Melee] BP_Boss_C_...   WeaponStart=缺失，WeaponEnd=缺失
  [Melee] BP_FightPlayer_C_0  WeaponStart=找到，WeaponEnd=找到
  ```
  **只有 BOSS 的插槽找不到**（玩家能找到）→ BOSS 的刀锋判定退化成
  "身体前方 40~120cm 的固定线段" → 与真实刀锋完全脱节。
- **修法（插槽全缺时改用骨骼推导刀刃）**：
  刀柄 = 持刀手骨（`hand_r/l`）；刀尖 = 沿"手→前臂"方向外推一个**刀长**。
  骨名多候选（`forearm/lowerarm/upperarm_r/l`）保证换骨架也能用。
- **⚠⚠ 关键二次发现（改完第一次仍然打不中）**：
  我最初直接把"前臂骨"当刀尖，实测日志显示判定线段**只有 32cm**：
  ```
  刀柄(-450,-180,176) 刀尖(-432,-197,156) 长度=32cm 半径=45
  ```
  前臂骨离手骨只有 32cm，判定球半径 45 根本够不到玩家（贴身有效距离远大于 77cm）
  → **仍然"BOSS 砍中了却查不到人"**。
  修正：前臂骨只用来定**方向**，刀尖按
  `max(WeaponTraceRadius*3.5, 骨骼盒半高*1.15)` 外推。
- **验证（同一份日志对比）**：
  | | 修前 | 修后 |
  |---|---|---|
  | 判定线段长度 | **32cm** | **157cm** |
  | 攻击采样中"查到可命中目标" | **0 条** | **764 条** |
  | 伤害结算 | 无 | **88.0** 正常 |
- **顺带修：`WeaponTraceRadius` 30 → 55**
  判定用的是"骨骼推导的虚拟刀刃"，不可能和真实刀刃完全重合，半径要留容错；
  55 略大于玩家胶囊半径(42)，贴身互砍稳定命中，又不会误伤背后的人。
- **预警红光与模型不重合（同一轮修复）**
  根因：`TelegraphFlashLight` / `HitFlashLight` 挂在**胶囊**上、偏移写死 Z=110/90，
  而 BOSS 的 Mesh 带 Yaw=-90° 相对旋转 + 每帧贴地校正 → 光和模型错位。
  修法：① 改挂 **Mesh**；② 每帧按【当前动画姿势的骨骼包围盒】校正灯的位置和
  衰减半径（`SyncLight`，只在灯亮时算，省开销）。
  新增参数 `TelegraphFlashRadius = 700` 作半径下限/基准。
  ⚠ 编译坑：lambda 形参名 `Mesh` 会 **C4458 隐藏类成员** → 改名 `MeshComp2`；
  `UPointLightComponent` **没有 `GetIntensity()`** → 改用 `IsVisible()` 判断。
- **新增诊断（以后这类问题能一眼定性）**：`[MeleeTrace]` 每次挥砍都打一行
  `采样点数 / 查到的Pawn / 可命中 / 新命中 / 刀柄刀尖坐标 / 伤害`。
  3291 条采样 → 立刻能看出"攻击了但查不到人"还是"压根没开窗"。

## 第二十轮：三个问题（无伤害 / 空步 / 只有前冲动画）—— 根因全在"细节被前面的架构改动打断"
- 用户报三件事：① 攻击动画播了没伤害 ② 移动还是空步 ③ 只有向前动画，要各方向。
- **根因 ①（无伤害）**：`[Melee] BP_Boss_C_... 武器插槽解析：WeaponStart=缺失，WeaponEnd=缺失`
  `ResolveWeaponSocket()` 只遍历 `UStaticMeshComponent`，而 **BOSS 的武器是骨骼网格组件** →
  两个插槽都找不到 → 判定退化成"角色身前 40~120cm 粗判线" → 砍中了也不判。
  玩家自己的武器是 StaticMesh 所以能找到 → **只有 BOSS 那边出问题**（这解释了"有些攻击没伤害"）。
  修法：新增第 3 步，遍历 `USkeletalMeshComponent`（跳过身体 Mesh 本身），先可见后不可见。
- **根因 ②（空步）**：`SmoothedLocoSpeed = Max(实测位移速度, Brain指令速度)`。
  Brain **每帧**都下令 → 意图一直为真 → 即使实测只有 6~127cm/s，
  倍速仍按指令值 380 算 → **腿全速倒腾、身体只挪一点点 = 脚底打滑**。
  修法：改成**只用实测位移速度**（`SmoothedLocoSpeed = bMovingNow ? MeasuredLocoSpeed : 0.f`）。
  倍速必须严格跟随身体真实速度，这是消空步的充要条件。
- **根因 ③（只有前冲）**：两层原因
  - a) `PickLocoWalkMontage()` 开头用 `GetVelocity()`，对 `RequestDirectMove` 驱动的 AI **恒为 0**
    → 每帧命中 `return Fwd`。改用本帧真实位移 `MoveDeltaThisFrame`（先算位移再推进采样点，顺序反了永远是 0）。
  - b) **更致命的一层**：`PlayGuardPose()` 用 `MeshComp->PlayAnimation(GuardMontage, true)`，
    它会把**单节点的 CurrentAsset 抢过去** → 行走蒙太奇被顶掉。
    实测：所有"速度=380"的采样，蒙太奇那一栏**全是** `Boss_Guard_Idle_Montage`
    → 移动时压根没有行走动画，只有一个举盾循环。
    修法：`PlayGuardPose()` 开头判断 `DebugPhysMoving || DebugMoveIntent` → 移动时 `StopGuardPose()` 并直接返回。
  - c) 方向兜底：`LastMoveCommandDir` 的写入函数 `NotifyBossMoveDirection()` **早就写好了但从没人调用**，
    而且它被放在 `protected:` 段里 → Brain 调不到（C2248）。
    现在 `DriveMoveNoNav` 每帧调用它，并把它提到 **public 段**。
    ⚠ 编译坑：`public:` 标签必须放在**声明之前**才生效（放在后面等于没加）。
- 验证：修复后"速度>100 时播的蒙太奇"从 `Boss_Guard_Idle_Montage` 变成 `无`（= 行走蒙太奇在播），
  说明行走动画终于能在移动时压过举盾姿势。
- ⚠ 无头环境的局限：无头对局里 BOSS 大部分时间在贴身对峙，采样到的"移动中"样本只有 1~7 个，
  **不足以统计四个方向动画的分布**。方向动画是否真的四向都播，必须靠 PIE 肉眼验证。

## 第二十轮：方向化行走失效（GetVelocity 恒 0）+ 攻击时序核查
- 用户反馈三件事：① 攻击动画在伤害之后才播 ② 还是太空步 ③ 移动动画只有"向前"一种。
- **③ 的根因（决定性）**：`PickLocoWalkMontage()` 用 `GetVelocity()` 算方向，
  而 **AI 直驱角色（RequestDirectMove）的 GetVelocity() 恒为 0**（CharacterMovement 已消费）——
  于是每帧都走 `return Fwd` 分支。日志实证：**21/21 帧行走动画全是 Boss_Walk_Fwd_Montage**，
  绕圈/后撤也在"往前跑" → 这就是"溜冰/空步"的直接原因。
  修法：改用**实测世界位移方向**（`CurLoc - LastLocoSampleLoc`），
  位移太小时退回 **Brain 下令的方向**（新增 `NotifyBossMoveDirection()` + 成员 `LastMoveCommandDir`）。
  ⚠ 与更早那次"速度要由 Brain 传"是同一个根因的两次发作：
  **AI 角色身上 GetVelocity 永远不可信，任何运动学判定都不能用它。**
- ① 攻击时序：日志核查**结论是正常的**——
  ```
  14:27:11:300 起手结束 → 出招「Slash_01」
  14:27:11:592 anim自检 蒙太奇=Boss_Slash_01_Montage 播放中=1  ← 动画立刻起播
  ```
  动画在出招同一帧起播，命中窗口按 `HitWindowStartRatio`（挥砍 0.22~0.36）延后开启。
  玩家看到的"伤害先于动画"更可能是**挥砍判定开得比视觉接触点早**，
  需要玩家指出具体是哪一招再逐招调 `HitWindowStartRatio`（不能盲调）。
- ⚠⚠⚠ **构建再次被 Live Coding 挡住**（第三次踩到）：
  `Unable to build while Live Coding is active` + exit 6 + 真实诊断 0 条。
