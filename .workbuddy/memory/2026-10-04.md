### 红光/绿光"不贴合"的真正原因 = 过曝，不是偏移
- 截图里那团"比 BOSS 还大的红色物体"其实是 BOSS 本身被自己的光吞了：
  Overlay 材质 `M_BossFlashOverlay` = Unlit + Additive，
  Emissive = Color × **Intensity(C++ 每帧写到 6)** × Flash × **(0.4 + 0.6·Fresnel)**。
  正面 0.4×6 = 2.4 的加法发光 → 整身烧成一片亮红 → Bloom 再糊一层 → 只剩红雾。
  Overlay 是逐像素作用在网格上的，物理上不可能跑出模型，所以"看起来不贴合"= 太亮太糊。
- 修法（材质被锁，先只改 C++）：
  · C++：`Intensity` 从 `1 + Pulse×5` → **`0.15 + Pulse×0.45`**（降约 10 倍），
    `Flash` → `0.65 + Pulse×0.35`。系数按**旧材质权重(0.4/0.6)** 反推。
  · 材质（已写进 `Tools/SetupBossVFX.py`，**尚未生效**）：
    Fresnel 权重 `0.4 + 0.6·F` → **`0.06 + 0.94·F^2.2`**（只有边缘烧）。
- 绿光：`UnstableOverlayIntensity` **改名** `UnstableGlowIntensity`，2.5 → 0.9。

## 预警红光"贴模型" + 倒地不移动（两件事一起改）

### 一、红光不贴合 —— 真因是【点光半径 7~10 米】，不是灯位
- 灯位其实每帧都对准了，但 `TelegraphFlashRadius=700` 被当作 clamp **下限**，
  `TelegraphFlashLightRadius=1000` 又在 UpdateTelegraphFlash 里每帧重设 →
  红光点光衰减半径是 7~10 米，把 BOSS 周围地面/空气全染红 = "一大坨光罩在人物外面"。
- ⚠⚠ **更隐蔽的坑：Tick 里同时存在两套灯位同步逻辑**（`UpdateFlashLightPositions()`
  ＋ 一个匿名 lambda `SyncLight`），后者排在后面、**直接覆盖前者**。
  行为完全取决于代码顺序。已删掉 SyncLight，只留一处。
- 点光源天生照亮范围内所有表面，想"贴合"只能把半径收到躯干尺寸：
  半径 = 躯干半高 × `TelegraphLightFitScale(0.7)`，clamp [70, 230]；
  强度按平方缩到 `TelegraphLightFitIntensity(2600)`（否则贴脸爆白）。全部用**新属性名**。
- 灯心偏低也是"不贴合"的一半原因：核心骨表里混了 `pelvis`，平均被拉到腰腿。
  去掉 pelvis + `Center.Z += 躯干半高 × 0.18`。
- 实测：半径 700~1000cm → **70~76cm**；灯心 Z 51cm → **132~145cm**（胸腔）。

### 二、★ 三条状态光抢同一个 OverlayMaterial 槽（新发现）
`USkeletalMeshComponent` **只有一个 overlay 槽**，而预警红 / 失衡绿 / 格挡冷蓝
三条通道各自直接 `SetOverlayMaterial()` → **谁最后跑谁赢**。
起手红光会把失衡绿轮廓整个顶掉 → 玩家看到"绿光时有时无"，读起来就是"绿光不贴模型"。
已改为：三条通道只各自置 `bXxxOverlayApplied` 标记，统一走 `RefreshBossOverlay()`
按优先级挂载（**起手红 > 失衡绿 > 格挡蓝**），并用 `AppliedOverlayMID` 避免重复 Set。
⚠ 这是"一个槽"类问题的通用教训：多个视觉通道共用同一资源槽时必须仲裁，不能各写各的。

### 三、倒地后不能移动
- `OnDeathReaction` 已经 StopMovement + DisableMovement + 关碰撞，**但拦不住每帧的东西**：
  ① `UpdateDisplacementGuard` 只把单帧位移夹在"走路速度 × 余量"（约 600cm/s），
     死亡后照样放行；它不但不拦，还会用 `SetActorLocation` 把尸体一路"夹"着滑出去；
  ② `UpdateSmoothFacing` 死了还能转身。
- 修法：新增 `UpdateDeathFreeze(DeltaTime)`，排在 Tick 最前 —— 记锚点，每帧
  `StopMovementImmediately + DisableMovement + 硬钉回锚点（位置/朝向）`。
  `UpdateSmoothFacing` / `UpdateDisplacementGuard` 各加 `IsDead()` 早退。
- 新增调试开关 **`demo.BossKill 1`**：走 `ApplyHit` 必杀（不是直接调 OnDeathReaction，
  保证是与实战同一条致死路径）。它顺带开启"死亡后每 0.5s 强行推 120cm + RequestDirectMove"
  的**外力压力测试** —— 没有它，"位移 0"可能只是场上恰好没人碰它。
- 实测：14 秒内被推 **1680cm，全部一帧内拉回**（单帧最大 120cm = 一次推的量），
  日志 `[Boss][死亡冻结] 累计被推 ≈ 已拉回`。取证日志保留在 UpdateDeathFreeze 里（每 1s 一条）。

## 破防跪地锁位 + 破防阈值 + 格挡率（第二轮）

### ★★ 破防阈值"调高"从来没生效过 —— 两层原因叠加（重要教训）
1. `ABossCharacterBase` 构造函数里**硬编码** `BalanceMaxPoise = 320.f;`
   → `Core/DemoCombatTuning.h` 的 `DemoBalance::BossMaxPoise`
   （2026-09-30 上调到 520、今天再上调到 720）**压根没有任何代码去读**，是死代码。
2. `BalanceMaxPoise` 是 UPROPERTY，BP_Boss 的 CDO 里序列化过旧值 → 改 C++ 默认值也压不过。
- 修法：① 属性改名 `BalanceMaxPoise` → **`BalancePoiseCap`**（CDO 旧记录作废）
  ② 构造函数改成 `BalancePoiseCap = DemoBalance::BossMaxPoise;`（tuning 成为唯一真源）。
- 教训：**改数值前先确认"这个数值真的被读到"**。日志 `[Balance] ... 韧性=320` 就是第一现场证据。
  凡"改了没生效"，第一反应应该是"值没被读到"或"CDO 压过"，而不是"数值不够大"。
- 实测：韧性 320 → **720**，70 秒内破防次数 2 → **0**。

### 破防跪地锁位
- 新增 `UpdateBreakFreeze(DeltaTime)`（Tick 里紧跟死亡冻结之后）。
  **与死亡冻结的关键区别：破防会恢复，所以不能 DisableMovement**，
  只锁位置 + 每帧 `StopMovementImmediately`，MovementMode 保留给起身用。
- 还要堵 `UpdateBossLocomotion`：破防期间若虚弱蒙太奇已播完，loco 会重新挂行走蒙太奇
  → "跪着滑行"。加 `if (IsPoiseBroken()) return;`。
  `UpdateSmoothFacing` 同样加破防早退（跪着转圈更怪）。
- 实测：两次破防期间累计被推 0.0cm / 已拉回 0.0cm。

### 格挡率 22% → 30%（用户反馈"BOSS 一味挨打"）
- 根因不是概率：`IsAttacking()` 读 GAS 的 `State_Attacking`，而那个标签覆盖
  **"预警→出招→后摇"整段** → 后摇（招式打完、位移结束）明明最该能防却被一起禁掉。
  实测 40 次命中里 20 次"无资格"。
- 改法：`bCommitted` 改成按 **Brain 状态机**判，只有 `Telegraph` / `Attack` 不挡，
  后摇 / 追击 / 走位 / 待机都允许。
- 数值（全部改名，新名字 CDO 无旧值）：`GuardRollChance 0.5→0.55`、
  `GuardRollCooldown 1.8→1.1`、`GuardPityHits 4→3`。
  （原 `BossGuardChance/BossGuardCooldown/BossGuardPityHits` 已改名）
- 实测：40 命中挡 12 = **30%**；有资格时命中率 50%（= 设定值），无资格 20→16。

### 通用教训
- "某状态下的移动/表现不对"，先查**每帧运行的全局系统**（位移闸、朝向、loco 仲裁），
  它们往往不看状态、死亡了/破防了照样跑。

## 角色/BOSS 在 FightArena 里"悬空"（用户截图反馈）—— 根因是场景网格的**单个大凸包**

### 症状与指纹
- 玩家和 BOSS 都浮在竞技场上方，脚不沾地
- 无头日志给出硬证据：`[Boss][空间诊断] 脚骨[foot_l] 世界位置=(43,-4670,**4175**)`
  而竞技场网格 AABB 的顶面恰好是 **4173** → 角色踩在**包围盒顶面**上，
  也就是被"包住整场的大凸包"托到了 41.7m 高（可见走道其实在 Z≈2475）

### 取证（新脚本 `Tools/ProbeArenaGround.py`，只读、不用开编辑器）
- `mesh.body_setup.agg_geom`：`box_elems=0, sphere_elems=0, sphyl_elems=0, **convex_elems=1**`
  → 这份 Fab 竞技场（103k 三角面）的简单碰撞就是**一个罩住 57m×144m 全场的凸包**。
  凸包把走道/台阶/柱廊等所有凹处全"填平"，胶囊只能停在虚拟斜面上
- 顺带证实：`get_actor_bounds()` 的"视觉 vs 碰撞"两侧**不可信**（都走 mesh bounds），
  别拿它当证据，要用骨骼世界坐标 / 凸包元素

### 修法（`Tools/FixArenaCollision.py`，无需改 C++、无需重新编译）
- `body_setup.collision_trace_flag = CTF_USE_COMPLEX_AS_SIMPLE`
  （编辑器里 = Static Mesh → Collision → Collision Complexity → Use Complex Collision As Simple）
- 简单查询改走**三角面** → 脚落在真大理石上；组件侧 `bUseComplexAsSimpleCollision` 默认 true，
  **不用改关卡 Actor**（少一处资产写入风险）；兜底地板保留当安全网

### 顺带修掉的"打不起来"

  而 `AggroRange=1600` → BOSS 全程 `Idle待机 距离=8555`，连追都不追。
  用 `Tools/MoveArenaSpawn.py` 把 PlayerStart 挪到 BOSS 面前 1500cm 并让双方互相面对
  （只改 PlayerStart 的 X/Y + 朝向，两侧 Z 保持用户肉眼验证过的原值，风险最小）

### 教训 / 容易踩的坑
- **"角色站在模型上却悬空" 先量脚骨 Z 是不是等于场景 AABB 顶**，是的话就是凸包问题，
  改动画/贴地代码/抬 PlayerStart 全都没用（凸包下一帧又把你顶回去）
- UE5.7 Python：**`unreal.KismetSystemLibrary` 已不存在** → `unreal.SystemLibrary.line_trace_single`；
  找不到库名就**扫描 `dir(unreal)` 找哪个类带目标方法**，比猜名字快
- **`unreal.Rotator(a,b,c)` 位置参数是 (roll, pitch, yaw)**：把 yaw 写进第 2 个参数会静默变成 pitch
  （第一版脚本因此把双方朝向全设错）→ 一律用关键字 `unreal.Rotator(roll=0,pitch=0,yaw=deg)`
- `unreal.Vector` **没有 `.size()`**；`set_actor_location` 三参必填
