## 锁定后 WASD 移动方向错误（已修，DLL 23:25:23）

**症状**：视角锁定后按 WASD，角色跑的方向和屏幕方向不一致。

**根因**：`AFightPlayerCharacter::HandleMove` 用
```cpp
const FRotator YawRotation(0.f, Controller->GetControlRotation().Yaw, 0.f);
```
换算世界方向 —— 基准是【控制器朝向】。而锁定后相机是用
`CameraBoom->SetWorldRotation(Smoothed)` 直接钉住的，**控制器朝向从没被更新**，
于是 WASD 仍按"锁定前那个朝向"换算：画面已经转过去了，方向没跟着转。

**修法**（`FightPlayerCharacter.cpp::UpdateLockOnCamera`，锁定分支）：
写完 `CameraBoom->SetWorldRotation(Smoothed)` 之后，每帧
```cpp
if (APlayerController* LockedPC = Cast<APlayerController>(GetController()))
{
    LockedPC->SetControlRotation(Smoothed);
}
```
只在锁定时同步 —— 自由模式下是鼠标驱动控制器朝向，反过来才对。

**附带修掉的两个副作用**
- 解锁瞬间相机接回 `PC->GetControlRotation()` 不再跳（两者本来就是同一个值）。
- `LockOnComponent` 筛选候选目标用的 `ViewForward` 也取自控制器朝向，同步后才准。

**判据（以后遇到同类问题的检查顺序）**
凡是"相机被代码直接改朝向"的架构（不走 `bUsePawnControlRotation`），
就必须同时回答：**谁在给 WASD 提供基准？** 答案是控制器朝向 → 必须显式同步。

## 贴身时的"卡模"与相机被身体糊住（处理中）

用户反馈：① BOSS 与角色靠近时**模型卡模**；② 锁定时贴身**看不见**（被某个模型糊满画面）。

**① 卡模 → 已改（待编译）**：`BossCharacterBase` 的
`MoveComp->MaxDepenetrationWithPawn` 从 **4 → 14**。
这个值原来压到 4（为了"温柔分开"），代价是分离速度只有 4cm/帧 ——
玩家持续往 BOSS 身上挤时胶囊推不开，网格一直嵌套。
14 是折中：≈840cm/s，几帧推开且远低于默认 32 的"一帧弹飞"。

**② 相机被身体糊住 → 待用户确认是哪个模型**（关键分叉）：
- 若是**自己角色的模型**：修法是"相机太近时把自己模型对本人隐藏"（`SetOwnerNoSee`，加迟滞防闪）。
- 若是 **BOSS 的模型**：说明相机钻进了 BOSS —— 需要让弹簧臂探测**命中角色胶囊**
  （`bDoCollisionTest` 虽为 true，但 `ProbeChannel = ECC_Camera`，
  而 Character 的 `Pawn` 碰撞配置对 Camera 通道是 **Ignore** → 探测根本打不到任何角色，
  相机于是可以穿进双方身体。BOSS 胶囊需 `SetCollisionResponseToChannel(ECC_Camera, ECR_Block)`；
  **玩家自己不能设 Block**（探针起点就在自己胶囊里，会瞬时塌缩成 0）。
- 几何上的硬约束：两人间距 <400cm 时，"相机离玩家 ≥280" 与 "相机离 BOSS ≥150" **无法同时满足**，
  必须选一边：**优先保离 BOSS 的距离**（贴着 BOSS 会看到身体内部，不可接受），
  玩家那侧靠隐藏自身模型解决。

## ★★★ 相机解算方向符号写反了（真正的大根因，已修，DLL 23:48:00）

用户补充："我的角色会在左下角靠近 boss 时**慢慢消失**" —— 这句是决定性的。

**查引擎源码定案**（`Engine/.../GameFramework/SpringArmComponent.cpp:185/187`）：
```cpp
DesiredLoc -= DesiredRot.Vector() * TargetArmLength;   // ← 减号：相机在枢轴【后方】
DesiredLoc += FRotationMatrix(DesiredRot).TransformVector(SocketOffset);
```
而 `UpdateLockOnCamera` 的迭代解算一直写的是
```cpp
const FVector CamPos = BoomOrigin + Desired.Vector() * ArmLen + ...;   // ← 错的
```
**这一个符号反了，同时造成了三个长期症状：**
1. **"锁了但没锁到 BOSS 身体中心"**：解算用的相机位置偏了 `2×臂长`（纯轴向），
   但肩位偏移的横向分量在这个错误位置上被放大 → 残余恒定 **7~8°** 偏移。
   （用日志反推也验证了：把 ±32° 的手动视角上限代入，"加法模型"要求 ViewYaw=-34° 越界 → 被排除。）
2. **"贴身疯狂抖动"**：错误方向上"相机离焦点的距离"被算成 `D − 臂长`，贴身时趋零 → 角度对距离极度敏感。
3. **"我的角色慢慢消失"**：因为方向反了，"臂长越长越危险"的判断也是反的 ——
   我上一轮加的"贴身收缩臂长"实际是把相机往**自己身体里**塞，近裁剪面切掉自身模型。

**修法**
- `CamPos = BoomOrigin - Desired.Vector()*ArmLen + Desired.RotateVector(SocketOff)`
- 肩位补偿分母改回加法：`CamToFocus = DistToFocus + ArmLen`
- **撤销自适应臂长**，回到固定 `LockOnArmLength=480`；删掉 `LockOnCameraStandoff` / `LockOnArmMin`
- 顺带把 header 里那段"贴身会爆炸到 58°"的错误推导一并改写（否则以后还会照着它改错）

**卡模**：`BossCharacterBase` 的 `MaxDepenetrationWithPawn` 4 → 14（分离速度 ≈840cm/s，几帧推开）。

**方法论教训（重要）**：涉及引擎组件行为时，**直接读引擎源码**，不要靠记忆或"看起来对"。
这次是靠 `SpringArmComponent.cpp` 一行代码结束了几天的反复猜测。
另外：`Saved/Logs/demo.log` 的原始日志比截图 OCR 可靠得多 —— 反推模型符号就是靠它的精确数值。
