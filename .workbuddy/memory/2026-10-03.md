## 第二轮：弹反后角色僵在那里 —— 移动锁是【布尔】而不是【引用计数】
- **根因**：`AFightPlayerCharacter::bMoveInputLocked` 原来只是一个 `bool`，
  而"锁移动"这件事**同时有 4 个技能各自独立持有**：
  `UGA_PlayerNormalAttack` / `UGA_PlayerParry` / `UGA_PlayerDodge` / `UGA_PlayerUseHeal`。
  任何两个都可能同时存在（弹反的 `CancelAbilitiesWithTag` 会取消普攻）。
  bool 的语义是"**谁最后写谁说了算**" → 必然互相误解锁：
  ```
  普攻 Lock(true) → 弹反取消普攻 → 普攻 EndAbility Unlock(false) → 弹反 Lock(true)
  若后两步顺序反了：普攻的 Unlock 会把弹反刚加的锁一起放掉（还能动但没锁住）
  反过来：弹反的 Unlock 提前放掉普攻的锁
  两者表现之一就是「弹反后角色僵在那里动不了」
  ```
  旧代码还写了"只在当前没被锁时才加锁、否则不记账"来试图规避，
  **换成引用计数后这个条件反而是错的**（会漏减）。
- **修法**：
  - `bMoveInputLocked: bool` → `int32 MoveInputLockCount`；
    新增 `LockMoveInput()` / `UnlockMoveInput()`，`SetMoveInputLocked(bool)` 保留成兼容包装。
  - 四个技能全部改成"**激活时无条件 Lock，结束/收招时配对 Unlock**"，
    各自用 `bLockedMoveXxx` 记账（这个记账现在是纯"我该不该减"的标记，不再判断别人锁没锁）。
  - 弹反的 `MaxWalkSpeed` 还原改成"**只有计数归零后才改**"，
    避免和普攻/闪避抢着改同一个值。
- **★ 兜底看门狗**（`FightPlayerCharacter::Tick`）：若 `MoveInputLockCount > 0`
  且**没有任何激活中的技能**（遍历 `ASC->GetActivatableAbilities()` 找 `ActiveCount>0`），
  持续超过 `MoveLockStaleTimeout`(3s) → 强制清零 + `MaxWalkSpeed` 还原 + 打 Warning。
  这样"任何一条加了锁没解锁的路径"（新技能忘了减、异常路径提前 EndAbility）
  都不可能让玩家永久卡死。宁可多放一次（下一帧有技能的会重新锁）。
- 编译坑（两个）：
  1. `UPROPERTY(BlueprintReadWrite)` **不能用在 private 成员**上 → UHT 报
     `BlueprintReadWrite should not be used on private members`（exit 6，当成"真实诊断"了）。
     调试阈值这类纯 C++ 成员就别加 UPROPERTY。
  2. **`TArray` 没有 `.Any()`**（`TMap` 才有）→ C2039。
     想写 "任意元素满足条件" 只能用普通 for 循环 + break。
     ⚠ 顺带记一笔：这次 exit 6 是**真错误**，不是 Live Coding（已用 `Get-Process` 确认没开编辑器）。
     判断方法仍是"真实编译诊断条数"：0 条才是 Live Coding，有几条就是代码错。

## 第三轮：攻击后动不了 —— 上一轮改引用计数时引入的【回归】
- **根因**：`UGA_PlayerNormalAttack::LockMovement()` 是从 **`PlayCurrentCombo()` 开头**调用的，
  也就是**连招每一段都会锁一次**（段数最多 4）。
  上一轮把移动锁改成引用计数时，普攻仍用单个 `bool bMovementRestored` 记账 →
  **锁 4 次只能减 1 次** → `MoveInputLockCount` 永久多 3 层 → 攻击后彻底动不了。
  连打越多次越僵。
- **同时发现的第二个 bug**：移速也每段都压一次 `MaxWalkSpeed *= AttackMoveSpeedScale(0.3)`，
  连打四段叠成 `0.3^4 ≈ 0.008%` → 就算解开锁也几乎不动。
- **修法**：
  - 头文件：`bool bMovementRestored` → `int32 MovementLockHeld`（本技能累计加锁几次）
    \+ `bool bSpeedReduced`（移速只压一次）。
  - `LockMovement()`：每次都 `LockMoveInput()` 且 `++MovementLockHeld`；移速仅在
    `!bSpeedReduced` 时压一次（基值固定用 `SavedMaxWalkSpeed`，可重复且幂等）。
  - `RestoreMovement()`：以 `MovementLockHeld <= 0` 作为幂等判据（**不再需要额外 bool**），
    循环减 `MovementLockHeld` 次；**只有 `!IsMoveInputLocked()` 时才还原移速**
    （否则会抢在闪避/弹反之前把它们的移速顶回去）。
  - `ActivateAbility` 开头重置 `MovementLockHeld = 0; bSpeedReduced = false;` 兜底。
- ⚠⚠⚠ **核心教训（换数据结构时的必查项）**：
  把"多持有者开关"从 bool 改成引用计数后，**必须重审所有"会重复调用加锁"的调用点**。
  bool 时代重复 Lock 无害（幂等），计数时代每次都 +1 → 必然泄漏。
  本项目里 `LockMovement()` 被 `PlayCurrentCombo()` 每段调一次，就是典型。
  判据：**搜"加锁函数名"，数它被几个调用点调用；再确认每个调用点都有一一对应的解锁**。
- 验证：60s 无头对局，`[MoveLock]` 告警 **0 条**、弹反看门狗 **0 条**。

## 第四轮：弹反后"愣神"——两个真 bug（都有日志铁证）
用户反馈"弹反后还是会愣神一段时间，动不了"。这次**日志直接给出了答案**，不用猜。

### ① 弹反后卡住 4.0 秒（技能不结束 → 普攻被标签挡住）
- **铁证**（`[Parry] ⚠看门狗触发：技能激活超过 4.0s 仍未结束 … 窗口=0 已弹到=1 窗口计时=0 收势计时=1 蒙太奇=0`）
  紧接着一连串 `[Fight] 尝试激活 GA_NormalAttack_C → 失败（标签阻挡/已在激活中）`。
- 解读：收势计时（`SuccessLockTask`）**已经跑完**（它不是 null，指针还在但已触发过），
  但技能没结束 → `UGA_PlayerParry::BlockAbilitiesWithTag` 还挂着 → 普攻一直被挡 = 玩家按啥都没反应。
- **根因**：`OnSuccessLockFinished()` 里的守卫
  ```cpp
  if (bWindowOpen || ActiveParryMontage) { return; }   // ← 只要有蒙太奇在播就永不结束
  ```
  `Parry_Hold_Montage`（持剑架势）时长长，于是收势计时一遍遍白跑，技能无限期挂着。
  **"收势计时"的语义本来就是"到点就兜底结束"**，不该等蒙太奇。
- **修法**：守卫只留 `bWindowOpen`（真在连弹）；其余情况先 `StopParryMontage()`
  再 `EndAbility()`。想继续连弹的玩家会重新按右键走 `OnRewindowEvent`，那条路径自己重建收势计时。

### ★★ ② 连招锁泄漏（锁层数一路涨到 15）
- **铁证**：`[MoveLock] ⚠ 锁层数 = 2 → 3 → 4 … → 15`（我上一轮加的告警正好抓到了它）。
- **泄漏链**（`PlayCurrentCombo` 里）：
  ```
  LockMovement()            → MovementLockHeld++     (为新段加锁)
  EndTask(ActiveRecover)    → 杀掉上一段的收招窗口任务
                              ↑ 而"解锁"正是由那个任务的回调 RestoreMovement() 做的
                              → 回调永远不会执行 → 那次 Lock 永远没有配对的 Unlock
  ```
  连打越多次，泄漏越多 → 彻底动不了。
  上一轮我只修了"记账方式"（bool→count），**没修"收招任务被杀"这个真正的泄漏源**。
- **修法**：`EndTask(ActiveRecover)` **之前**先 `RestoreMovement()` 把上一段的锁还清，再 `LockMovement()`。
  `RestoreMovement` 以 `MovementLockHeld<=0` 幂等，天然安全。

### ⚠ 方法论教训（这轮最有价值的一条）

  → 症状相同（都是动不了）的 bug，根因可以完全不同，**必须靠日志区分**。
- **告警日志的价值**：上轮加的 `[MoveLock] ⚠ 锁层数 = N` 这条，
  本轮一眼就定位到"锁涨到 15 层"。**给"可累加的状态"加一条带数值的告警，
  比事后读代码猜有效得多**。
- 复现注意：无头 bot **不一定会弹反**（要看 BOSS 何时出招），

### ★★★ 根因 1：方向分类【写死了 X=前后 / Y=左右】，但实测角色正前方是 +Y
- 我加了一条诊断日志 `[Boss][方向诊断]`，一次性打出：

- **结论**：BP_Boss 的 Mesh 带 Yaw=-90° 相对旋转 → **Mesh 空间的 Y 轴才是角色正前方**。
  而旧代码 `bForward = Local.X >= 0` 把 +X 当"前" → **BOSS 朝玩家走被判成"向右横移"** → 播 Strafe。
  这正是用户说的"面向角色追踪却是侧着走"。

  但**只换了坐标系，没换轴**——Mesh 空间里的"前"是 Y 不是 X，换了空间却仍按 X 判，前后正好差 90°。
- **修法**（`PickLocoWalkMontage` + `PickLocoJogSequence` 两处都改）：
  ```cpp
  // 不写死轴，运行时测量角色正前方在 Mesh 空间的方向
  const FVector FwdInMesh = MeshXf.InverseTransformVectorNoScale(GetActorForwardVector()).GetSafeNormal2D();
  const FVector RightInMesh = FVector::CrossProduct(FwdInMesh, FVector::UpVector).GetSafeNormal2D();
  // 把移动方向投影到"前/右"两个基
  FwdComp   = RawDir.X*FwdInMesh.X   + RawDir.Y*FwdInMesh.Y;
  RightComp = RawDir.X*RightInMesh.X + RawDir.Y*RightInMesh.Y;
  ```
  骨架换了、Mesh 旋转改了都自动正确。
- ⚠ 编译坑：`RawDir` 是 `FVector2D`、基向量是 `FVector`（3 分量），
  `FVector::DotProduct(RawDir, FwdInMesh)` → **C2664**，必须显式写 2D 点积。
  另外 `Local` 是 `const` → 不能回写，改用新变量 `FwdComp`/`RightComp`。

  还是别的原因（不合理）。

### ★ 空步：这轮找到两个真实的参数级原因
1. **`LocoDirSwitchAngleDeg` 从 50° 降到 22°**
   50° 太宽 → 绕圈时方向已经明显变了但动画不换 → 腿朝旧方向蹬、身体朝新方向平移
   → 脚在地上横向拖 = 滑步。22° 仍够宽容（不因噪声乱换）。
2. **倍速平滑太慢（起步滑出）**
   `FInterpTo(MeasuredLocoSpeed, FrameDelta, dt, 20.f)` 要 ~0.15s 才收敛，
   而 BOSS 起步时位移是**阶跃**的 → 腿按 0.6 倍速慢动作爬、身体按 380 平移 → 脚往前滑。
   修法：上升沿强制 `SmoothedSpeed = max(平滑值, 实测*0.7)`，
   下降沿仍走平滑（避免抖腿）。两条路径（蒙太奇分支 + 正常路径）都要改。
   ⚠ `MeasuredSpeed` 是 `const` → 结果写进成员 `MeasuredLocoSpeed` 再统一用。

### ★★ 关于无头跑的一个教训（之前误判了）
- 我曾报告"100% 行走帧位移 < 2cm → BOSS 根本没在动"——**那是无头跑的假象**。
- 真相：无头 `-NullRHI` 只跑了 **390 帧 / 60 秒 = 6.5 FPS**，
  每帧位移自然小（380cm/s ÷ 6.5fps ≈ 58cm……但采样点对齐后统计出来很小）。
  重新统计：中位 7.8cm、p90 9.9cm、最大 1225cm（起步那一帧），**移动是正常的**。
- → **无头跑的"每帧位移"类统计在低帧率下完全不可信**。
  判据要改用"整局累计位移"（本项目 3408cm，正常）或 p90 分位数，不要看中位数。
  更重要：**动画空步这类问题必须用 PIE 或视频验收，无头跑看不出来。**

## 第七轮：★★ 硬直才是"一顿一顿"的真凶（不是移动被吞）

### ★★★ 决定性数据：`Stagger硬直` 占 BOSS 状态 31%
心跳状态分布（修前）：
```
Chase追击      48 (31%)
Stagger硬直    47 (31%)   ← 和 Chase 一样多！
Attack出招中   37 (24%)
```
**BOSS 有一半时间在被定身**。原因：`bAlreadyStaggered` 只防"连击刷硬直"，
但**不防"每刀之间冷却"** —— 玩家每砍一刀，0.28s 硬直就吃掉一次，
于是移动变成【走一截、停一下、再走一截】→ 行走动画永远走不完一个完整步态
→ **正是用户说的"一顿一顿的地面平移 / 太空步"**。
⚠ 之前我一直在查"移动指令为什么只有 10 次"，方向完全错了：
移动逻辑没问题，**是被硬直一次次打断的**。

  冷却内照样播受击动画（视觉有反馈）但**不定身**，BOSS 能连续走位。
  动作游戏里硬直是【偶尔的奖励窗口】，不是常态。
- **验证（决定性）**：
  ```
  修后：Chase 42% / Attack 27% / Recover 18% / Telegraph 12% / Stagger 0%
  ```
  **`Stagger硬直` 从 31% 彻底归零**，`Chase` 反而上升。移动连续性恢复。

### 新需求 2：BOSS 格挡（不要太频繁 + 要有蒙太奇）

  动作游戏里"被格挡"是**偶发事件**，用来提醒玩家"别无脑连段"；每次都格挡会很挫败。

- 格挡成功 → **直接 return**：不播受击动画、不进硬直（伤害照常结算，所以不会"格挡了不掉血"）。
- 只在 BOSS 空闲时格挡（`!bCommitted`），否则叠在出招上会动不了。
- ⚠ 无头跑 0 次触发（bot 打不中 BOSS），需 PIE 验收。

### 问题 A：BOSS 仍然不格挡 —— 真因是【常驻 State_Blocking 挡了 70%，而它绕过概率判定】
- 加了调试 CVar `demo.BossGuardTest N`（BOSS 每 1.2s 挨一刀），`Tools/RunHeadlessGame.py`

  **根本没调 `TryGuardIncomingHit` → 举盾蒙太奇一次都不播**。玩家只能从"伤害变小"去猜，
  于是得出"BOSS 根本不会格挡"。

### 问题 B：起步地面平移 —— 已根治，并把最后一截尾巴也砍掉
